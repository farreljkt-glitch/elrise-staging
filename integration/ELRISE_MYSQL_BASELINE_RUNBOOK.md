# Elrise production-safe Prisma baseline — 2026-10-13

## What this contains

Versioned initial MySQL schema migration `prisma/migrations/20261013000000_initial_baseline/migration.sql`, generated by **Prisma 6.19.3** from the full current `prisma/schema.prisma`. It creates all schema tables (including `AdminInvitation`) and the current `ADMIN_PROJECT` role and project assignment relation. CI deploys it to a **disposable, empty `elrise_ci` MySQL 8** instance with `npx prisma migrate deploy`, then runs schema, transaction rollback, real HTTP/tenant-scope, account onboarding/offboarding tests. CI also checks the committed SQL matches a fresh schema diff. This is *not* a production deployment.

## STOP: existing local/staging/production Elrise databases

**Do not run `prisma migrate deploy` on your current populated `elrise_db` yet.** This is an initial migration from an empty database and includes `CREATE TABLE` statements. Applying it directly to an already populated DB can fail; never drop existing tables or `prisma migrate reset` just to make it pass.

1. Freeze schema writes briefly and create an encrypted, access-controlled backup/snapshot of the **actual Elrise database only**, including MySQL schema, data and triggers as applicable.
2. Clone the live *Elrise* DB to an isolated staging MySQL instance. Do not copy real personal data into CI; sanitize data in test environments.
3. With reviewed, securely stored `DATABASE_URL` pointing to the *clone*, run a **read-only schema drift inspection**:
   `npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --exit-code`
   Exit code **0** means the schema matches; code **2** signals differences; other codes indicate an error. Record the differences for review. Never silently run `db push` against real data.
4. If the clone **already exactly matches** the current Prisma schema and no Prisma migration history exists, then and only then evaluate baselining with:
   `npx prisma migrate resolve --applied 20261013000000_initial_baseline`.
   This records the baseline in `_prisma_migrations` without rerunning the initial CREATE statements. **Resolve still mutates migration metadata**, so carry it out on the cloned DB first, after backup and explicit review.
5. If the clone differs from schema, **do not** falsely mark it as baselined. Prepare ordered, reviewed forward migration(s) matching real current state, preserving existing tenant, employee, loan and payroll rows. Test each on the clone and compare counts/checksums before and after.
6. Verify restore from backup in a separate environment. Document downtime/lock impacts, rollback, and cutover. Then schedule the real Elrise DB migration with operator approval.

## Fresh staging installs only

On a brand new, empty and disposable MySQL schema dedicated to Elrise:
`npx prisma migrate deploy`
then `npx prisma migrate status`.
This installs the initial baseline, not Gajiku schemas. Never direct `DATABASE_URL` to `gajiku_db`.
